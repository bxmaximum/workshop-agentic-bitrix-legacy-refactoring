# Bitrix code review · ревью-агент с чек-листом

## Что это и чего это не делает

Скилл для **второго агента**: он не писал код и не будет его чинить. Его работа — прочитать код по чек-листу и выдать
отчёт, который человек прочитает за пять минут, а третий агент превратит в красные тесты и фикс.

- **Код не меняется.** Ни правок, ни «быстрых фиксов», ни форматирования. Режим Ask/Plan или явное «не трогай файлы».
  Если ревьюер нашёл ошибку и очень хочется починить — это находка в отчёт, не коммит.
- **Каждая находка — с `файл:строка`.** Находка без строки — не находка, а мнение. Строки берутся из реального файла,
  не по памяти.
- **Ранжирование обязательно.** Отчёт без серьёзности превращается в шум за неделю, и его перестают читать.
- **Известное не повторяется.** Если в проекте есть реестр багов (`docs/bugfix_plan.md`, `docs/legacy/*.md`) — сначала
  прочитать его. Находка, которая уже там, упоминается одной строкой со ссылкой на номер, а не расписывается заново.

## Когда применять

- Ревью PR или ветки перед мержем: область — `git diff <base>...<head>` плюс файлы, которые дифф вызывает.
- Ревью модуля или компонента целиком: после рефакторинга, перед релизом, при передаче кода.
- Повторное ревью после фикса: проверить, что находка закрыта тестом, а не только кодом.

Не применять для стилистики и форматирования — на это есть линтеры.

## Порядок работы

1. **Определить область.** Дифф — `git diff --stat`, список файлов. Модуль — `find … -name '*.php'`. Записать список в
   отчёт: что смотрели, что нет.
2. **Прочитать контекст.** `AGENTS.md`, реестр известных багов, `.settings.php` модуля (какие контроллеры, сервисы),
   `install/index.php` (что ставит), точки входа: `www/<раздел>/*.php`, `ajax.php`, `Controller/*.php`, шаблоны.
3. **Открыть `rules/checklist.md`** и пройти по классам. Для каждого класса там есть команды поиска: сначала grep, потом
   чтение найденных мест целиком, а не только совпавшей строки.
4. **Подтвердить находку.** Где возможно — воспроизвести запросом: `curl` на эндпоинт без `sessid`, GET на мутирующий
   URL, спецсимволы в параметре. Если воспроизвести нельзя — так и написать: «по коду, не проверено».
5. **Ранжировать** по правилам ниже и написать отчёт по формату.
6. **Закончить списком «проверено и чисто»** — что искали и не нашли. Без этого раздела непонятно, смотрели ли вообще.

## Ранжирование

| Серьёзность | Критерий | Что делать |
|---|---|---|
| **критично** | Эксплуатируется снаружи без авторизации или ведёт к выполнению чужого кода/SQL, подделке действия пользователя, чтению чужих данных | Чинить до мержа. Красный тест обязателен |
| **важно** | Нарушение инварианта проекта, утечка данных при авторизованном доступе, отсутствие проверки там, где данные меняются, архитектурный красный флаг из `AGENTS.md` | В план, срок — до релиза |
| **замечание** | Небезопасный паттерн, который сейчас прикрыт (escape есть, но в другом месте), дублирование, мёртвый код, неточность в сообщении | Бэклог с датой или «принято, не чиним» с обоснованием |

Если сомневаешься между двумя уровнями — ставь выше и объясни, почему сомневаешься.

## Формат отчёта

Файл `docs/review/<ГГГГ-ММ-ДД>-<область>.md`, например `docs/review/2026-09-18-vacancies.md`.

```markdown
# Ревью: <область> · <дата>

**Область:** <ветка/дифф/модуль>, файлов: N. **Не смотрели:** <что и почему>.
**Известные баги:** учтён реестр <путь>; находки, которые там уже есть, помечены номером.

## Находки

| № | Серьёзность | Класс | Файл:строка | Что не так | Как исправить | Как проверить (уровень теста) |
|---|---|---|---|---|---|---|
| 1 | критично | CSRF | lib/Service/VacancyResponseService.php:34 | POST формы не проверяет sessid (баг №11) | check_bitrix_sessid() до валидации, ошибка с кодом csrf | Feature: POST без sessid → 200 и текст ошибки, редиректа нет |

## Проверено и чисто
- SQLi: сырой SQL только в Repository/*, значения через forSql/(int); ORM select/order — из констант. Файлы: …
- …

## Решения (заполняет человек)
- №2 — принято, не чиним: <обоснование>.
```

Столбец «Как проверить» — с уровнем: `Unit` (чистая функция), `Integration` (сервис/репозиторий на ядре), `Feature`
(HTTP-контракт: статус, заголовки, JSON), `e2e` (браузер, JS). Находка без теста на неё закрывается «по слову», а слово
через месяц никто не вспомнит.

## Чего не делать

- Не менять код, тесты, конфиги. Не запускать команды, которые пишут в базу или репозиторий.
- Не писать «возможно, стоит подумать о…». Либо находка с файлом и строкой, либо её нет.
- Не переписывать реестр известных багов своими словами — ссылка на номер.
- Не выдавать за критичное то, что прикрыто на другом уровне (например, сырой SQL с `forSql` внутри Repository).
  Раздел «что не является находкой» в `rules/checklist.md` — читать до отчёта, не после.
- Не растягивать: 3–7 находок в отчёте читают, 25 — нет. Замечания одного типа группируются в одну строку
  со списком мест.
