# Чек-лист ревью Битрикс: SQLi · XSS · CSRF · права · остальное

Для каждого класса: где искать (команды), что считать находкой, как исправлять (ссылка на эталон в
`.agents/skills/bitrix-security/rules/*.md`), как проверять тестом. Grep — только отправная точка: найденное место
читается целиком вместе с вызывающим кодом.

Обозначения: **Ф** — находка, **НФ** — не находка (см. последний раздел).

---

## 1. SQL-инъекции (SQLi)

Эталон: `bitrix-security/rules/sql-ssrf.md`, раздел «SQL Injections».

### Где искать
```
grep -rn '\$DB->Query\|->query(\|queryExecute(\|ForSql\|forSql\|SqlExpression\|ExpressionField' www/local
grep -rn 'setOrder(\|setSelect(\|->order\|"order" =>\|\x27order\x27 =>' www/local
grep -rn 'whereLike\|LIKE' www/local
```

### Что считать находкой
- **Ф критично.** Строковая конкатенация значения из запроса в SQL без `(int)`/`forSql`: `"WHERE ID = " . $_REQUEST['id']`,
  `"LIKE '%" . $q . "%'"` без `forSql($q)`.
- **Ф критично.** Имя поля или направление сортировки из запроса в `setOrder()`, `setSelect()`, ключах `filter`
  (`'>' . $userField`), в `ExpressionField`/`SqlExpression` без плейсхолдеров `?#`, `?s`, `?i`. Значения в `filter`
  параметризуются, **ключи — нет**.
- **Ф важно.** Сырой SQL вне слоя Repository (в компоненте, шаблоне, сервисе, ajax-скрипте), даже если экранирован:
  нарушает границу, и следующая правка сделает его небезопасным.
- **Ф важно.** `$DB->Query($sql, true, …)` — второй аргумент `true` глушит ошибки; ошибка SQL в проде останется незамеченной.
- **Ф замечание.** Сырой SQL в Repository там, где есть ORM-эквивалент (`whereIn`, `ExpressionField('COUNT(*)')`).

### Как исправлять
D7 ORM `query()->where()`; для сырого — `(int)` для чисел, `$helper->forSql()` для строк, `prepareInsert/prepareUpdate`
для массивов; в `SqlExpression` — плейсхолдеры. Белый список для `order`/`select`.

### Как проверять
Integration: репозиторий с `q = "x' OR 1=1 --"` возвращает пустой список, а не все записи; `sort=views' --` даёт
сортировку по умолчанию. Unit: нормализация сортировки отдаёт только значения из белого списка.

## 2. XSS и экранирование вывода

Эталон: `bitrix-security/rules/csrf-xss.md`, раздел «XSS and HTML Sanitization».

### Где искать
```
grep -rn '<?=' www/local/components www/local/modules/*/install/components | grep -v 'htmlspecialcharsbx\|GetMessage\|Loc::'
grep -rn "\['~" www/local          # сырые ~KEY
grep -rn 'TEXT_TYPE.*html\|nl2br(' www/local
grep -rn 'json_encode\|<script' www/local/components
grep -rn 'href="<?=' www/local/components
```

### Что считать находкой
- **Ф критично.** Вывод в шаблон значения, которое пришло из запроса или от неадминистратора, без `htmlspecialcharsbx()`:
  поле формы в `value=""`, параметр `q` в тексте, сообщение об ошибке с подставленным вводом.
- **Ф важно.** Вывод `~KEY` (сырого значения) или поля с типом `html` (`PREVIEW_TEXT`, `DETAIL_TEXT`) без санитайзера,
  если это поле редактируют не только администраторы. Если только администраторы — **замечание** с пометкой «доверенный
  ввод, но санитайзер стоит».
- **Ф важно.** Данные в `<script>` через конкатенацию вместо `\Bitrix\Main\Web\Json::encode()`; данные в `data-*`
  атрибутах без экранирования.
- **Ф важно.** URL, собранный конкатенацией параметра без `urlencode`/`http_build_query` — и XSS через `javascript:`,
  и разрыв параметров (`&` в значении).
- **Ф замечание.** Экранирование «в двух местах»: `NAME` экранирован в презентере и ещё раз в шаблоне (`&amp;amp;`),
  или наоборот — контракт `KEY`/`~KEY` нарушен и непонятно, кто отвечает.
- **Ф замечание.** `strip_tags()` как единственная защита: режет теги, но не атрибуты в уже существующих.

### Как исправлять
`htmlspecialcharsbx()` на выводе; для HTML от пользователей — `CBXSanitizer` с уровнем `SECURE_LEVEL_HIGH`; для JS —
`Json::encode`; для URL — `http_build_query` или `urlencode`. Контракт `$arResult`: `KEY` экранирован, `~KEY` сырой,
и шаблон выводит `KEY`.

### Как проверять
Feature: GET с `q=<script>alert(1)</script>` → в теле `&lt;script&gt;`, сырого `<script>` нет. e2e: `assertSourceHas('&lt;')`
для текста, `assertSee('<')` для отображения. Unit: презентер экранирует `NAME`, `~NAME` оставляет сырым.

## 3. CSRF и мутирующие запросы

Эталон: `bitrix-security/rules/csrf-xss.md`, разделы «CSRF» и «CSRF Details»; `bitrix-controllers/rules/filters.md`.

### Где искать
```
grep -rn 'check_bitrix_sessid\|bitrix_sessid_post\|bitrix_sessid()\|X-Bitrix-Csrf-Token' www/local
grep -rn 'DisablePrefilters\|Csrf::class\|HttpMethod' www/local/modules/*/lib/Controller
grep -rn '\$_POST\|getPost(\|isPost()\|REQUEST_METHOD' www/local
grep -rn 'fetch(\|BX.ajax\|runAction' www/local/components www/local/modules/*/install/components
```

### Что считать находкой
- **Ф критично.** Обработчик формы или ajax-скрипт, который пишет в базу/сессию/почту без `check_bitrix_sessid()`.
  Наличие `bitrix_sessid_post()` в форме без проверки на сервере — та же находка: поле рендерится, но не работает.
- **Ф критично.** Контроллер с `#[DisablePrefilters([ActionFilter\Csrf::class])]` на экшене, который меняет состояние.
  Проверить, что отключение не унаследовано: `configureActions()` и `getDefaultPreFilters()`.
- **Ф критично.** Мутирующее действие по GET: `?action=favorite&id=N`, `?delete=1`. GET не должен менять состояние
  вообще; CSRF-токен на GET — полумера.
- **Ф важно.** Контроллер в `SCOPE_REST` или своём scope без собственной проверки: фильтр `Csrf` работает только в
  `SCOPE_AJAX`.
- **Ф важно.** JS отправляет POST без `sessid` в теле и без заголовка `X-Bitrix-Csrf-Token` — сервер либо не проверяет
  (критично, см. выше), либо запрос сломан.
- **Ф важно.** Нет `#[HttpMethod([METHOD_POST])]` на мутирующем экшене контроллера: токен проверяется, но действие
  доступно и через GET-ссылку.
- **Ф замечание.** Комментарий вида «sessid отключён, ломало мобильное приложение» без даты и тикета — это находка на
  процесс: решение принято, но не зафиксировано.

### Как исправлять
Форма: `bitrix_sessid_post()` + `check_bitrix_sessid()` первым действием обработчика, ошибка с отдельным кодом.
Контроллер: не отключать `Csrf`, добавить `#[HttpMethod([ActionFilter\HttpMethod::METHOD_POST])]`. JS: `BX.ajax.runAction`
(токен добавляется сам) или `fetch` с `X-Bitrix-Csrf-Token: bitrix_sessid()`. Легаси-клиенты, которым нужен GET, — отдельный
эндпоинт с собственной авторизацией и сроком жизни.

### Как проверять
Feature: POST без `sessid` → ошибка и запись не создана (проверить счётчик до/после); с `sessid` из GET той же сессии → успех.
GET на мутирующий URL → ошибка, состояние не изменилось. Integration: сервис отдаёт `Result` с кодом `csrf`.

## 4. Права доступа и авторизация

Эталон: `bitrix-security/rules/jwt-crypto-access.md`, раздел «Access Rights»; `bitrix-controllers/rules/filters.md`,
`#[ActionAccess]`.

### Где искать
```
grep -rn 'NOT_CHECK_PERMISSIONS\|CHECK_PERMISSIONS\|IsAuthorized\|IsAdmin\|CanDoOperation\|GetUserRight' www www/local
grep -rn 'Authentication::class\|ActionAccess\|getCurrentUser\|CurrentUser::get' www/local/modules/*/lib
grep -rn 'USER_ID\|OWNER\|CREATED_BY' www/local/modules/*/lib/Service www/local/modules/*/lib/Controller
```

### Что считать находкой
- **Ф критично.** Чтение или изменение чужой записи по `ID` из запроса без проверки владельца (IDOR): «мой отклик» по
  `?response_id=N`, «удалить избранное» с чужим `USER_ID`.
- **Ф критично.** Административное действие (модерация, смена статуса, экспорт) в публичном контроллере без
  `Authentication` и проверки права.
- **Ф важно.** `define('NOT_CHECK_PERMISSIONS', true)` в точке входа, которая отдаёт не только публичные данные, или
  `CHECK_PERMISSIONS => 'N'` в выборке, где права инфоблока значимы. Если эндпоинт заведомо публичный и только читает —
  **замечание** с формулировкой «зафиксировать, что публичный».
- **Ф важно.** `#[DisablePrefilters([ActionFilter\Authentication::class])]` на экшене, который пишет. Для гостевых
  действий (отклик, избранное в сессии) — допустимо, но тогда должен быть лимит: троттлинг, капча или сессионный ключ.
- **Ф важно.** Проверка `$USER->IsAdmin()` скопирована в каждый экшен вместо фильтра или `#[ActionAccess]`.
- **Ф замечание.** `global $USER` в сервисе: сервис зависит от HTTP-контекста; заменить на параметр `userId`
  или `CurrentUser::get()` в точке входа.

### Как исправлять
Фильтры контроллера (`Authentication`, `#[ActionAccess]`), проверка владельца в сервисе через `Result`, права инфоблока
через `CHECK_PERMISSIONS => 'Y'` там, где они настроены. Публичные эндпоинты — явно помечать в `.settings.php` и в
комментарии.

### Как проверять
Feature: тот же запрос из двух сессий — вторая не видит и не меняет данные первой; неавторизованный запрос на
административный экшен → `401`/ошибка. Integration: сервис возвращает ошибку с кодом `access_denied` для чужого `userId`.

## 5. Остальное, что ловится тем же проходом

- **Open redirect.** `LocalRedirect($request->get('back'))` без проверки, что URL внутренний — **важно**.
  Исправление: `\Bitrix\Main\Web\Uri` и проверка хоста, или белый список путей.
- **Массовое присваивание.** `Table::add($request->toArray())` или `add($_POST)` — **критично**: пользователь задаёт
  `STATUS`, `USER_ID`. Исправление: DTO с явными полями.
- **Инъекция в письмо.** Поля пользователя в `CEvent::Send` без очистки переводов строк в полях-заголовках
  (`EMAIL_TO`, тема) — **важно**. Тело письма — через `htmlspecialcharsbx` в шаблоне события.
- **Раскрытие ошибок.** `ShowError($e->getMessage())`, `exception_handling.debug => true` в проде, стек в JSON —
  **важно**.
- **Троттлинг только в сессии.** Лимит «раз в минуту» по `$_SESSION` обходится новой cookie — **замечание**, с пометкой,
  что для публичной формы нужен лимит по IP/капча.
- **Сессия как хранилище состояния.** `$_SESSION` напрямую вместо `Application::getSession()` — **замечание**
  (тестируемость, `CloseSession`).
- **Секреты.** Ключи, пароли, токены в коде или в `.settings.php`, который в репозитории — **критично**.
- **Загрузка файлов.** Проверка только по расширению, сохранение под именем пользователя, путь из запроса — **критично**.

## 6. Архитектурные красные флаги D7 (из `AGENTS.md`)

Это не безопасность, но ревью-агент их отмечает как **важно**/**замечание**, потому что они делают следующий
инцидент вероятнее:

- Бизнес-логика или запросы к БД в контроллере, компоненте, шаблоне (толстые входы).
- Исключение как единственный канал ошибки через границу сервиса вместо `Result`.
- Конструкторная инъекция в `Controller`, консольную команду, обработчик события.
- `$_GET`/`$_POST`/`$_REQUEST`/`$_SERVER` вне точек входа; `global $DB`/`$APPLICATION` в `lib/`.
- Роуты в `.settings.php` модуля вместо `/local/routes/`.
- Нет `declare(strict_types=1)` в новых файлах `lib/`.

## 7. Что **не** является находкой

Чтобы отчёт не превращался в шум:

- Сырой SQL внутри `Repository/*` с `(int)`/`forSql`/`quote` для всех значений, если ORM-эквивалента нет
  (например, прямой доступ к `b_iblock_element_prop_m<N>`) — максимум **замечание**.
- `DisablePrefilters([Authentication::class])` на экшене, который только читает публичные данные.
- `NOT_CHECK_PERMISSIONS` в точке входа, которая только отдаёт публичный список и помечена как публичная.
- Вывод `~PREVIEW_TEXT` типа `html`, который заполняют только администраторы, — **замечание**, не важно.
- Известный баг из реестра проекта (`docs/bugfix_plan.md` и т. п.) — одна строка со ссылкой на номер, без нового
  описания. Исключение: если реестр оценивает серьёзность ниже, чем этот чек-лист, — сказать об этом.
- Стиль, форматирование, именование, длина методов — не для этого скилла.
- «Можно было бы кешировать» — не безопасность и не корректность; отдельное ревью производительности.

## 8. Быстрая самопроверка отчёта

- [ ] У каждой находки есть `файл:строка`, серьёзность, класс, способ проверки с уровнем теста.
- [ ] Критичные — воспроизведены запросом или помечены «по коду, не проверено».
- [ ] Известные баги — только ссылкой на номер.
- [ ] Есть раздел «проверено и чисто» с перечислением, что искали.
- [ ] Ни один файл кода не изменён: `git status` пустой, кроме `docs/review/`.
