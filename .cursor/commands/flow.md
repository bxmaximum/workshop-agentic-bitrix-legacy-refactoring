# /flow — запустить конвейер «задача → PR»

Явно запускает конвейер разработки по стадиям в этом чате (см. правило
`00-flow-orchestrator` и скилл `flow`).

Использование: `/flow <описание задачи>`

## Настройка в начале (до clarifier)

Перед делегированием `clarifier` оркестратор **обязательно** задаёт три вопроса
и фиксирует ответы в `docs/flow/<slug>/01-task.md` (раздел «Настройки flow»):

### 1. Кто контролирует гейты?

| Режим | Поведение |
|-------|-----------|
| **Пользователь** (по умолчанию) | Оркестратор останавливается на каждом гейте, показывает резюме и ждёт решения человека. |
| **Агент** | Оркестратор **полностью играет роль пользователя**: сам отвечает на вопросы clarifier, выбирает вариант, утверждает план, подтверждает готовность к финалу. Решения принимает обоснованно, как если бы пользователь явно согласился. Не останавливается на гейтах и не спрашивает подтверждения. |

### 2. Что делать по завершении flow?

| Режим | Поведение |
|-------|-----------|
| **Заявка / без git** (дефолт для IPS) | Рабочая копия **не в git**. Ветки/коммиты/push/PR **не делать**. После гейта 3 `integrator` готовит handoff: список изменённых файлов + краткая заявка для внешней команды. |
| **PR** | Стадия 6: `integrator` пушит ветку и открывает PR со squash commits. Мердж — вручную. Только если появится доступ к git-репо. |
| **Мердж в основную ветку** | После гейта 3 `integrator` пушит ветку и **мерджит в основную ветку** (`master` / базовая ветка из `project-context`) со squash commits. PR не создаётся. |
| **Оставить в ветке** | После гейта 3 `integrator` **не вызывается** (или только коммитит/пушит ветку без PR и без мерджа). Фича остаётся в feature-ветке для ручного ревью позже. |

Если в корне рабочей копии нет `.git` — автоматически выбирай **«Заявка / без git»**, даже если в Delivery указан git-режим.

### 3. Нужен ли отчёт для задачи?

| Режим | Поведение |
|-------|-----------|
| **Нет** (по умолчанию) | Отчёт не составляется. |
| **Да** | После гейта 3 оркестратор пишет `docs/flow/<slug>/04-report-bitrix.md` — готовый текст для публикации в Битрикс24. |

**Требования к отчёту** (аудитория: PM и клиент):

- Отвечает на **постановку задачи**: что требовалось → что сделано → какой результат для бизнеса/пользователя.
- **Без технических подробностей**: без имён файлов, пакетов, внутренней архитектуры, diff'ов. Допустимы понятные формулировки уровня «добавлен эндпоинт», «исправлена ошибка при поиске».
- **Не поверхностный**: конкретика по сути изменения, ограничения и что не вошло в scope (если есть) — но кратко.
- **Компактный**: ориентир — ½–1 экрана текста, не эссе. Структура: постановка → результат → как проверить/что заметит пользователь → при необходимости оговорки.

Оркестратор показывает черновик отчёта перед финалом; в режиме «гейты — пользователь» можно поправить, в режиме «гейты — агент» — финализирует сам.

Если пользователь не ответил — уточни один раз. Не начинай clarifier, пока все три ответа не зафиксированы
(в режиме «гейты — агент» оркестратор может выбрать разумные дефолты сам и зафиксировать их).

## Стадии

1. **Уточнение и варианты** — настройка flow (гейты + финал + отчёт), затем субагент `clarifier`
   изучит репозиторий и вернёт вопросы + 1–3 варианта.
   В режиме «гейты — пользователь»: ты ответишь и выберешь вариант. **(ГЕЙТ 1)**
   В режиме «гейты — агент»: оркестратор сам ответит и выберет вариант.
2. **План** — субагент `planner` пишет подробный план в `docs/flow/<slug>/`.
   В режиме «без git» ветку **не** создаёт. Иначе — создаёт `<type>/<slug>`.
   В режиме «гейты — пользователь»: ты утвердишь план. **(ГЕЙТ 2)**
   В режиме «гейты — агент»: оркестратор сам утвердит план.
3. **Реализация** — субагент `implementer` выполнит план.
   С git — коммиты на чекпоинтах; без git — только правки файлов + список изменений.
4. **Ревью** — субагент `reviewer` проверит изменения и запишет `03-review.md`;
   цикл исправлений через `implementer` до чистого вердикта.
5. **Целостность** — субагент `docs-keeper` обновит документацию, ADR, правила,
   скиллы и субагентов.
   В режиме «гейты — пользователь»: ты подтвердишь готовность. **(ГЕЙТ 3)**
   В режиме «гейты — агент»: оркестратор сам подтвердит готовность.
5b. **Отчёт для Битрикс24** (если выбрано на стадии 1) — оркестратор составляет
   `04-report-bitrix.md` по требованиям выше и согласует/финализирует перед финалом.
6. **Финал** — по выбранному режиму завершения:
   - **Заявка / без git** — `integrator` готовит handoff (файлы + текст заявки), без git-операций.
   - **PR** — `integrator` пушит ветку и открывает PR; мердж вручную.
   - **Мердж** — `integrator` пушит и мерджит в основную ветку.
   - **Ветка** — работа завершена в feature-ветке, без PR и без мерджа.

Для мелких задач стадии 1–2 могут объединяться. Тривиальные однострочные правки выполняются без конвейера.

Все роли конвейера — субагенты **Cursor Task** (`.cursor/agents/`).
